# 原生桥提交结果不明保护

日期：2026-11-01；分支：`refactor/reliable-channel-core`。

## 问题与修复

旧实现先调用 `chat.stream`，随后保存 preamble、turn 和 spool 偏移；调用超时或后续本地保存异常时，会把原消息交给备用收件箱。平台可能已经开始执行，备用路径或重启后再次提交会重复产生副作用。可选 merge 路径也存在类似问题。

现实现先将 `submission_pending` 和消费的 spool 连续前缀同次保存，再发出外部调用。记录包含原消息、路由、会话 ID、回复基线和队列字节范围。成功返回后才把意图转为普通运行记录；任何提交中或提交后错误保留待核查记录，不转备用、不重发。

普通和 merge 提交结果不明时，worker 在处理边界变更、读取新队列、取消、轮询、空闲扫描之前进入保护。该桥当前按渠道维护 worker，因此暂停范围是该渠道的原生提交，不具备按聊天独立恢复的能力。其他渠道及既有独立备用入口不由该保护接管。

`/check` 优先显示“任务提交结果待核查，已暂停新任务”，不引导用户重发。通知使用保留的原消息路由，正常保存通知标记后不重复提醒。通知与状态仍是两个文件写入，不承诺崩溃窗口内通知恰好一次。

取消 RPC 失败时保留运行记录并进入现有退避流程，不再把“取消请求失败”当作任务已停止。只有调用返回成功才结束取消路径，平台最终取消语义仍需真实 SDK 联调验证。

状态写入使用 `0600` 权限、文件同步、原子替换及父目录同步。提交意图保存失败时不调用外部执行。已存在状态文件损坏、权限异常等错误直接阻止处理，不再视为空状态从头重放；只有文件不存在才初始化。

## 核查与恢复边界

旧 Muse 接口没有本模块可依赖的持久请求/run 关联标识。某条历史回复出现在基线之后，不能单独证明它属于这次结果不明的提交，所以本次不自动取历史结果并解除保护。

出现保护时，由主会话读取 `submission_pending` 并核查平台原会话与运行记录，确认原任务是否接受、仍在执行、已完成或明确未提交。证据须结合原消息、会话、时间、实际执行及副作用；不能仅凭暂时查不到结果判断未执行。

本次未提供自动解除或手工清空命令。不要删除 pending、回退 spool 偏移、删除状态文件或重复发原任务来恢复。确认结果后应通过经过验证的核查适配工具提交状态转换；该工具和平台联调属于下一阶段工作。需要人工处置时保留原状态快照，先停止相关写入者，再制定与证据一致的恢复操作。
