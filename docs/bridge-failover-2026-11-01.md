# 桥故障时的网关备用路径

本修复适用于 legacy 模式中启用桥分流的个人微信和企微单聊文字。网关按渠道检查桥 worker 心跳和持久状态；桥明确不可用且没有在途任务、未知提交或桥队列积压时，新消息写入 inbox，由 hook 处理。

网关分流和桥工作步骤使用同一渠道文件锁。判断与写入在锁内完成，网关等待锁的过程放在后台线程。写入桥队列或 inbox 前检查两条队列中的相同消息与路由；半行或损坏记录不会被当作安全切换依据。桥自身在提交前失败需要转备用时，只有没有其他积压工作才切换，否则保留队列等待桥恢复。

首次切换会写入持久 `.fallback-weixin` 或 `.fallback-wecom` 标记。即使桥重新在线，后续消息仍走备用路径，桥也不会领取该渠道的新工作；这是为了避免备用任务尚在执行时两条路径同时处理。切换后不会自动解除标记。网关和桥必须都升级到支持相同锁的版本，旧进程不会遵循新锁。

## 恢复桥路径

先确认该渠道网关和 hook 已处理完所有降级消息，核查正在执行、等待发送和结果不明的任务及其实际投递状态；同时确认桥 state 中没有 submission_pending、活跃 turn、recovery_queue 或 spool 积压。仅当这些证据完整且 bridge 服务健康时，由维护人员停止相关写入者，在渠道 route 锁保护下移除对应 fallback 标记，再启动并先用一条普通文本验证。若有未知结果、损坏状态或未送达消息，保留标记并先核查，不凭心跳推断完成。

锁与检查仅约束升级后的参与进程；关闭分流标志的管理操作、非分流的群聊及附件仍沿用原有处理路径，不能视为通用跨路径串行保证。健康检查后再发生外部环境故障时，已写入 spool 的消息会等待桥恢复，不会另写 inbox。缺失或损坏的桥状态无法证明没有在途工作，保守保留在桥路径。

本地验证：33 组沙箱套件、571 项检查通过，包含真实网关回调、锁竞争、积压、去重和状态损坏场景；尚需在 Linux/systemd 测试部署中演练进程中断与恢复。
