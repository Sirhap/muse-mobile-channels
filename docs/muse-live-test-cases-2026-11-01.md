# Muse 实测用例：微信、企微和桥故障恢复

日期：2026-11-01

待测分支：`refactor/reliable-channel-core`；最低代码提交：`2eeeb02`。请在实际测试记录中填写当前完整 commit。本文面向部署在 muse.ai 的 Muse 助手及手机端操作者。

## 测试约定

- 优先在隔离的 Linux/systemd 测试环境、测试机器人和测试会话执行。每个实际启用的渠道分别验证；未部署的渠道记“未测”，不算通过。
- 先确认测试环境、运行模式（legacy/core）、代码 commit、网关/桥/hook 版本和渠道。本文桥降级用例只适用于 **legacy 模式且启用对应桥分流的单聊文字**；core 模式、群聊及附件不按该降级结论验收。
- 测试仅使用唯一的无敏感标记，例如 `MUSE-TEST-WX-01`。不要在报告里粘贴 token、cookie、聊天正文、用户 ID 或未经脱敏的完整状态文件。
- 所有停服务、断网、故障注入、状态调整、清除标记和服务切换都可能影响生产；先准备具体环境、范围、恢复步骤并取得用户同意。不得对正在执行的真实任务操作。没有独立环境或未获同意时，跳过故障注入并说明原因，继续可安全执行的只读检查和普通消息测试。
- “已入队”“平台已接收（ok=true）”和“手机实际看到”分开记录；不能仅凭服务 active 或心跳判断端到端成功。异常时保留脱敏证据，不反复重发可能已经执行的任务。

## A. 测试前检查

1. 在部署目录执行 `git rev-parse --abbrev-ref HEAD`、`git rev-parse HEAD`，核对进程实际启动路径是否指向该检出目录；版本不一致先停止，避免新旧代码混用。
2. 确认网关与桥都已更新到同一版本；旧进程不会遵守新路由锁。记录各相关 systemd 服务状态和 hook 是否运行，核查状态与队列是否有未知提交、活跃任务、未处理消息和未完成投递。存在不明在途任务时，不做故障切换。
3. 检查桥对应渠道 `status.json` 中 `mode`、`worker_heartbeat`，以及 `state.json` 中对应渠道的 `turns`、`submission_pending`、`recovery_queue` 和 spool offset。仅记录字段状态和数量，勿复制内容。
4. 运行仓库沙箱测试 `python tests/run_core_regression.py`，记录 Python 版本、通过/失败数量。不能运行则记录具体原因，不把旧版本或本地 macOS 结果当成 Linux 结果。

## B. 普通功能（每个启用渠道执行）

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| B01 | 手机发送 `/ping`，再发送包含唯一标记的简单问题 | pong 到达；普通问题收到一次对应答案。记录队列、平台接收结果和手机实际展示。 |
| B02 | 连续发送两条可区分的问题 | 两条均收到对应回复，无跨会话串答、重复或无关断线提示。 |
| B03 | 先聊一个主题，发送 `/new` 后发新问题 | 换会话回执与运行模式一致；后续问题使用新上下文。旧长任务若稍后完成，应能识别其原问题，不能误作新问题答案。 |
| B04 | 用可安全取消的长任务测试 `/stop` | 回执仅表示取消请求已登记；核查平台是否确认停止。取消请求失败或结果未知时，不判定已停止、不自动重跑。 |
| B05 | 发送小图片/文件并请求回传测试文件 | legacy 模式核对实际内容与文件收到；core 模式媒体适配尚未完成，应记录明确的不支持反馈，不记作功能通过。 |
| B06 | 用测试审批触发允许或拒绝 | 只有显式授权的会话和操作者可决策；重复点击不重复提交。检查平台实际决定；core 审批链未完成则标未测。 |
| B07 | 从其他测试用户或群聊尝试同一审批/群管理命令 | 未授权请求被拒绝，原审批和其他会话任务不变；不向其他聊天泄露审批内容。 |

## C. 桥失效与备用路径（仅隔离环境）

每次执行前先核查该渠道没有 `submission_pending`、活跃 turn、recovery_queue 或 spool 积压；验证已经完成的回复实际送达。操作涉及服务和路由，执行前取得用户对具体操作的同意。

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| C01 空闲断桥 | 按已批准步骤停止测试桥进程，保持测试网关和 hook 可用；发送单聊唯一标记 | 网关确认桥不可用且无在途/积压后写该渠道 inbox，由 hook 处理；手机收到一次答案。确认未写入桥 spool 且出现对应 `.fallback-<channel>` 标记。 |
| C02 桥恢复后 | C01 的备用任务尚未全部结案时，按批准步骤恢复桥，再发送第二个唯一标记 | 降级标记仍在，第二条继续进入 inbox；桥不领取该渠道新工作，不出现两条路径同时执行或重复回复。 |
| C03 备用完成后恢复桥 | 核查所有备用消息的执行、发送及未知状态；桥 state 无在途/积压。准备并获批恢复方案后，在共享渠道 route 锁保护下解除对应降级标记，发送第三个标记 | 桥路径恢复后第三条只进入 spool 并收到一次回复。无法核实或有未知结果则保留标记、停止并记录。 |
| C04 桥有积压 | 在隔离环境按批准方案让桥 spool 保留未处理消息后使桥不可用，再发新消息 | 不把新消息转 inbox 超越积压；原 spool 保留，待桥恢复或人工核查。不得直接复制旧消息到 inbox。 |
| C05 在途或提交未知 | 用隔离测试桩/经过授权的故障注入，使外部提交的结果不明，再发一条新消息 | `submission_pending` 保留；该渠道原生提交暂停，原消息不自动重发或转备用。`/check` 提示待核查。不得靠删除状态解除。 |
| C06 重连和提示 | 在隔离环境模拟桥连接/业务调用持续失败 | 两次普通失败之间按实现退避，连续 3 次失败后暂停；同一未恢复故障不应每小时重复刷屏。核查日志和用户提示一致。 |
| C07 桥停止后恢复 | 在不触碰 C05 未知任务的前提下，批准并执行桥进程停止/恢复演练 | 已写 spool 的消息由桥恢复处理，不再复制到 inbox；逐条核对唯一标记没有重复执行或遗漏。 |

状态缺失、损坏、权限不可读、队列半行或来源不明时，应保守保留并报告；不能把“读不到状态”当作“没有在途任务”。健康检查和真实平台状态之间仍有不确定性，记录实际操作与现象。

## D. 安全核查和验收结论

- 记录每条测试消息的唯一标记、入队位置、实际执行次数、对应发送结果和手机展示；对不上时先核查，不以多发一次消息验证。
- 若发现重复执行、跨会话泄漏、未确认取消被当作停止、状态损坏后继续执行，立即停止受影响测试并保留证据。
- 降级标记、服务状态和测试配置仅按已批准恢复方案处理。对提交结果不明的任务，只有可靠核实原消息、会话及实际副作用后，才考虑使用 [桥提交恢复说明](bridge-submission-recovery-2026-11-01.md) 和当前 CLI 的核查入口；无证据不得重发。
- 最终按渠道列出通过、失败、未测及原因。明确真实 Muse SDK/run 关联、媒体、审批和 Linux 故障演练是否验证；不要把模拟测试报告为真实渠道通过。恢复桥的详细条件见 [桥故障恢复说明](bridge-failover-2026-11-01.md)。
