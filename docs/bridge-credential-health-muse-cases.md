# 桥凭证健康修复：Muse 实测清单

目的：验证 Cookie 失效不再被 token 回退掩盖，审批中继不再每 20 秒无效重连，恢复提示有真实 RPC 证据，普通消息和长任务能完成交付。每次执行填写实际版本、时间、通过／失败／未测及脱敏证据；本文件不是线上验收通过记录。

## 1. 实测准备

- 记录 `git rev-parse HEAD`、实际运行目录、Python/SDK 来源、已启用渠道与 legacy/core 模式。核对部署确实加载本次代码，不只看 Git 分支名。
- 先只读检查现有在途任务、`submission_pending`、备用接管标记和队列。涉及生产部署、服务重启、状态迁移或故障注入时，先给具体步骤和恢复方案并取得同意；故障注入默认在隔离部署完成。
- 使用测试账号和已核实的通知会话。保留正常凭证私有备份，目录 `0700`、文件 `0600`；不把真实凭证、Cookie/Authorization 头、账号 ID、审批正文写进报告。
- 本地 mock 测试只能证明故障处理逻辑。真实 Cookie 失效、平台连接和手机收发需要在 Muse 环境取得证据；不能假造平台 401 代替线上认证实测。

## 2. 分来源认证与恢复

用户安装 [浏览器扩展](../native-bridge/muse-cred-extension/README.md)，在已登录的目标 Muse 会话导出完整 `muse-credentials.zip`，通过安全文件投递交给 Muse。Muse 先临时解压检查，核对 Cookie、VM、token 完整且 VM 与预期一致，备份后安装到实际凭证目录。VM 不一致则停止安装；不要直接覆盖切到其他 VM。

在与服务相同的 SDK、用户和凭证目录下运行只读检查：

```bash
~/muse-test-venv/bin/python ~/workspace/native-bridge/check_credentials.py --source all --json
```

若目录不同，通过 `NATIVE_BRIDGE_CREDENTIALS` 指定实际目录；不要在命令行展开或输出 `NATIVE_TOKEN_JSON`。token 检查优先使用当前进程的环境 token，否则读 `token.json`；存在环境覆盖时不代表磁盘 token 已验证。逐项记录 Cookie 桥查询、token 桥查询与 Cookie 审批查询的状态、来源和检查时间；任一失败应保留失败状态，不能由另一路成功覆盖。

验活是主动只读 RPC 检查，不代表服务重连已执行、暂停状态已解除或真实消息已投递。确认实际服务随后发生一次成功操作及对应状态更新，再进入消息验收。SDK 不可用或验证未运行记为“未验证”，不能写“认证恢复”。

## 3. 故障、重试与通知（隔离环境）

| 场景 | 操作与通过标准 |
| --- | --- |
| Cookie 文件损坏，token 有效 | 使用测试凭证夹具使 Cookie 解析失败；桥仍验证 token 并能返回客户端，Cookie 保持失败；失败客户端释放，无原始错误或凭证泄露。 |
| Cookie 401，token 有效 | Cookie 首次明确认证失败即提醒，说明桥可用 token 回退、Cookie 路径有问题；不能宣称审批恢复。相同故障后续周期和进程重启不重复故障通知。 |
| 两路失效 | 桥报告全部不可用，仍遵循原三次失败后暂停；不重复提交已提交任务，不删除未知提交记录。 |
| 降级后全断 | 先确认 Cookie 失败而 token 回退通过，再使 token 失败；必须补一条状态升级提醒，不能一直停留在“token 回退可用”。同一故障的升级提醒只发一次。 |
| 审批 Cookie 认证失败 | 首次失败通知一次；600 秒内无新认证连接；最多三次失败后暂停。主循环继续检查文件变化，不以“循环仍在运行”当成仍在联网重连。 |
| 重启与凭证变化 | 中继重启保持原失败预算和停连状态；只更新 token 不唤醒中继；更新 Cookie 或 VM 元数据立即允许重试。VM 变化仅在隔离夹具验证，生产不擅自更换 VM。 |
| 普通网络故障 | 模拟连接超时；分类为网络，不能提示 Cookie 已过期。仍受有界重试约束，不制造无限连接循环。 |
| 通知通道故障 | 只安装微信或企微时可通知可用渠道；全部 outbox 不可写时保留待通知状态。恢复可写后重试相同事件 ID；不将通知错误记成认证错误。 |
| 恢复通知 | 桥对应来源 `sessions.list` 或审批 `egress.approvals` 实际成功后，每个服务的同一故障各发一次恢复提醒。仅构造客户端、token 成功、进程 active 均不能恢复 Cookie 健康。 |
| 再次失效 | 已实际恢复后出现新故障，可以开启新的故障／恢复事件；旧的通知去重不能永久屏蔽新事故。 |
| 环境覆盖 | 注入测试用 `NATIVE_TOKEN_JSON`，确认桥优先使用它；诊断标明环境来源，不把磁盘 token 未检查误报为通过。 |

记录连接尝试时间、重试次数、暂停标志、来源状态、稳定通知事件 ID 及通知投递结果。不要为缩短实测临时修改生产默认超时；本地自动测试可用受控时钟验证 600 秒边界。

## 4. 真实入站与正式回复

每个已启用渠道都执行：

1. 用户先发 `/ping`，确认网关可达；再发一句带本次唯一测试标记的普通问题。
2. 记录这条问题的入站 msgid、实际走桥还是备用路径、正式回复的队列 ID。若路由到备用路径，单独记录，不能认定原生桥收发通过。
3. 用该渠道 CLI 的 `results --limit <覆盖本次记录的数量>` 按确切队列 ID 查结果。只有对应记录 `ok=true` 才写“网关确认平台接收”；用户可补充手机可见证据，不能写“用户已读”。进度 update 或入队成功不能代替正式回复。
4. 确认桥失败计数已由成功操作清零、Cookie 与 token 状态分别显示，审批真实查询成功。未配置某渠道或无测试审批时标“未测”，不猜测通过。
5. 若存在备用接管、未知提交或在途审批，按 [桥故障恢复说明](bridge-failover-2026-11-01.md) 核对并制定切流方案，不清空状态来制造通过结果。

## 5. 长任务与交接

先核对平台当前安装的 hook 定义与仓库版本，收集原任务 run_id 对应的：worker 注册／进度／hold／handoff 时间、心跳循环启停原因、平台终态及检查时间、取消记录、正式回复队列 ID 与投递结果。只报告字段与时间，聊天正文和凭证不进入报告；缺证据时原中断原因仍记“待证实”。

在隔离环境发起一个预计超过 15 分钟的正常任务，观察以下顺序：

1. 批次开始用本次真实 run_id 登记 `heartbeat-start`；约每 2 分钟给一次有内容的 update，并执行 `cancelled` 与 `worker-activity --beat --progress`。进度与实际阶段对应，不运行空心跳来掩盖停工。
2. 预计长工具或等待前登记合理的 `--hold-secs`。任务继续执行时约第 13 分钟续期 `heartbeat-start`，核对同一 msgid、run_id、进度和 hold 未丢失。跨 15 分钟时，实际活动或有效 hold 应避免误判中断。
3. 工具结束后清除或更新 hold，继续正式工作并最终 reply。核对回复队列 ID 与 `ok=true`，不能把持续心跳等同于任务完成。
4. 对基础设施修改任务，渠道 worker 先正式回复说明移交未完成，再登记 `worker-activity --handoff`，调用实际可用的主会话交接工具，带上 msgid、run_id、队列 ID、成果和待验证项。工具不存在或通知失败须如实报告，不宣称移交成功。
5. 主会话接手并交付最终结果；检查交接保护能覆盖原 worker 结束，但不会无限保活。24 小时保护过期与无活动场景用本地受控时钟测试，不在生产等待或伪造平台记录。

2026-11-04 补充：后续监管修复将无可靠平台终态的静默任务置为“待核查”，不自动重派或取消；活动写入携带当前 `--run-id`，同 run 心跳续期不刷新真实活动。验收以 [长任务待核查说明](task-interruption-review-2026-11-04.md) 为准，保留本节关于真实进度、hold 与正式交付的要求。

本地组合回归检查两渠道真实 CLI 的登记、进度、hold、续期和交接记录与存活探针配合；它不启动真实后台心跳进程，不证明线上调度器或通知工具已正常工作。
