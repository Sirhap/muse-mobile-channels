# 长任务中断：待核查处理与 Muse 验收

## 证据与修复边界

依据用户提供的 `task-interruption-evidence.md`，11 月 4 日 15:52 的任务走微信 hook worker；16:22 自动续跑一次，16:55 由 hook fail-stop 登记取消。两轮没有绑定原消息的进度或正式回复，第二轮只有注册记录；没有该任务的平台执行裁决。900 秒后台心跳退出不是取消动作，不能拿它证明 worker 已死。

旧监管策略把静默当作恢复／取消的充分条件。本地用真实双渠道 hook 与隔离状态复现了同形行为：活动距今 1798 秒时保留，1803 秒时进入第二次静默停止。修复采用用户确认的策略：执行状态未知时先待核查并提醒接手，确认原执行结束后才允许后续自动恢复或停止。1800 秒观察窗、900 秒心跳上限、hold 与交接保护时长不延长。

该证据仍不能解释原 worker 为什么停止产出。首轮 run_id 未保留、平台执行记录缺失，且部分 workspace 文件在事发后变过；此次修复的是能复现的监管误判路径和关联记录缺口，不声称找到了平台执行中断根因。

## 新行为与兼容性

- 无新鲜活动、无当前 run_id 的新鲜平台终态时，登记 hook state 下的 `worker_review.json`，排入一次待核查提醒。它不证明存活、完成、成功移交或人工已接手；提醒仍需投递结果确认。
- 待核查任务不进入自动重派、orphan 或防饿死补派；也不自动写取消。新消息照常处理，原 worker 的迟到正式回复仍可走正常投递路径。
- 平台裁决必须包含与当前登记完全一致的非空 run_id，且检查时间新鲜。缺失、过期、错 run、unknown 和探针异常都不能授权恢复／取消。用户主动停止和实际投递成功的正式回复继续有效；hold、交接保护继续优先。
- 确认原执行结束后仍最多自动续跑一次，并持久化本次恢复消耗的原 run_id。即使续跑 worker 还没登记，原 run 的终态也不能被重复用来停止它；只有明确的新 run 登记及其新鲜终态才允许第二次停止。旧记录缺少恢复来源身份、恢复预算损坏或无法落盘时保留待核查，不猜测恢复是否已发生。裁决文件不会取消底层平台执行，只为 hook 提供监管证据。
- worker 当前活动仍按 msgid 保存；不同 run 接管时保存最多 8 份 `previous_runs` 快照，并保留精简的退休 run_id 集合，禁止旧 run 再抢回登记。新 run 不继承旧进度、hold 或交接保护。
- 同 run 的 `heartbeat-start` 续期保留已有进度和 hold，但只更新登记观察时间，不刷新真实活动时间。接管后 beat、hold、handoff 必须携带当前 `--run-id`；旧 run、缺少绑定的操作失败，不能先停掉或启动别人的心跳。

`heartbeat-stop` 同样支持 `--run-id` 并在接管后要求匹配；`/queue`、`/status` 单列待核查，不把它报为运行中或空闲。用户可在原会话发送 `/stop` 登记取消待核查任务，登记不证明底层操作已经结束。活动记录保留既有损坏自愈兼容行为；发生记录损坏或历史缺损时，不能用重建后的空历史推断旧执行已结束，仍须平台核查。

hook state 中的 `recovery_attempts.json` 是恢复预算与来源 run 的权威账本，先持久化再派工；`resume_attempts.json` 保留旧时间戳镜像。旧镜像有预算但缺来源身份时，按“预算已消耗、恢复归属待核查”处理，不自动认定当前执行就是第二轮。不要删除这些文件来强行重试；写入失败后原执行、派工结果和已有产物需由管理员核对。

## Muse 部署与核查步骤

1. 先记录当前部署版本、实际 hook API 定义、脚本路径和现有在途任务。部署、服务重启、切流或故障注入先给出步骤与回滚办法，获准后执行；不要清空 pending、cancelled 或队列来制造通过。
2. 同步仓库中的公共 Python 模块、双渠道 CLI、存活探针、hook 脚本与定义。`worker_supervision.py`、`credential_health.py`、`channel_common.py` 必须位于同一仓库根目录，探针及脚本使用实际部署路径。只拉 workspace 代码不等于更新了 `~/hooks/scripts/`；定义／提示词通过平台 hooks API 更新，轮询至少 5 秒。
3. 在隔离环境按下表故障注入，分别验证微信和企微。记录版本、msgid、每轮 run_id、监管状态、提醒队列 ID 和真实投递结果，报告中不放 Cookie、token 或聊天正文。
4. 待核查出现后，主会话或管理员按 [平台核查 runbook](worker-platform-check-runbook-2026-10-15.md) 查询确切 run。查不到就保留待核查并说明阻碍；不能伪造 shutdown、修改活动时间或用 detached 心跳代替执行证据。
5. 查询确认已终止且仍需处理时，让正常监管读取裁决。先核查已生成产物和外部操作，再从断点处理；真实平台原执行未确认结束前不另起相同任务。人工不希望续跑时，明确停止原消息。

## 验收场景

| 场景 | 通过标准 |
| --- | --- |
| 两轮长期静默、无平台裁决 | 均进入待核查，不增加恢复次数，不写取消，不重派；提醒只入队一次，状态可跨 hook 轮询保留。 |
| 不完整或过期裁决 | 缺登记、裁决缺 run_id、错 run、过期或 unknown 都不能停止任务，探针不可用同样不能停止。 |
| 确认原执行已结束 | 相同当前 run 的新鲜终态允许一次续跑；恢复 worker 尚未登记时，重复的原 run 终态不能取消任务；新 run 登记后旧裁决失效。第二轮也确认结束且无回复时才走停止。预算不可读／不可写时不得唤醒。 |
| 待核查期间新消息 | 新消息正常唤醒，旧消息不混入新 worker 的任务列表。 |
| 正式回复迟到 | 不因待核查取消或丢弃；只有对应正式回复队列 `ok=true` 才判该消息交付完成，进度和入队成功不足以结案。 |
| 用户停止、hold 与交接 | 用户停止继续生效；有效 hold／交接保护优先；保护过期只触发重新核查，不自动证明死亡。 |
| 真实活动与续期 | 同一 run 正常进度、hold、心跳续期配合；单纯反复续期不能无限刷新真实活动。任务无总时长硬上限。 |
| 新旧 run 并发 | 新 run 不继承旧 hold；旧 worker 的注册、beat、hold、handoff 被拒绝，不改变当前记录或心跳进程。批量登记冲突不能部分提交。 |
| 提醒写入故障 | outbox 不可写保留待提醒，恢复后稳定队列 ID 去重；入队后尚无结果不重复发，明确未发送的死信才允许重试。 |

本地自动回归只能证明调度和记录逻辑；真实平台查询、主会话接手和手机可见结果须由 Muse 实测记录。原事故的具体执行停止原因继续标为未证实。
